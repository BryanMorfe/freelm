# Bots

Bots are a separate, host-owned messaging surface. They use the app's existing connections and model catalog without depending on whichever Chat/Code workspace is open. They have no direct shell, filesystem, computer-use, or arbitrary MCP access; they delegate work to Chat and Code through the tools below. Users can separately grant specific account-connected [plugin tools](PLUGINS.md) directly to individual bots in Settings → Plugins. These grants are independent of Chat/Code history access and rechecked on every call. Reaction notifications expose no plugin tools.

## Planned external messaging

The [deferred Slack plugin proposal](SLACK_PLUGIN.md) describes individually addressable bot identities, two-way conversations, reminders, and task updates. Slack connectivity is not implemented yet.

## User flow

- Open Bots below Home. Create a bot with a name, address, color, identity, connection/model, and thinking mode. Addresses are unique on a host; routing always uses a stable host ID plus bot ID, never an address alone.
- Click a bot to open its direct conversation. Enter sends, Shift+Enter inserts a newline. Messages clear after durable acceptance. The bot can finish replying while another FreeLM screen is open.
- Message menus offer reactions, reply, copy, and (for user messages) edit/unsend. Unsending clears the stored message content and cancels pending replies. Editing a trigger with pending replies cancels and replaces those replies. Completed replies are retained.
- New group selects multiple local/connected remote bots and a conversation host. Each participant gets a turn to consider a human message, using its own model and identity; a reply is optional. New bot messages can wake the other participants. The coordinator sends the group transcript and roster to each participant's host. Bot identities and learned notes stay on their home hosts.
- Bot details show identity, learned notes, home, and model. Customize lets users review/edit notes or disable Chat/Code thread access, learning, or the bot. Disabled bots remain accessible to re-enable.

`@freelm` addresses are in-app identifiers, not email accounts. A disconnected remote must reconnect before accepting new messages. Existing loaded history stays readable. Bots can follow up on delegated work, reactions, and [saved schedules](SCHEDULER.md) while FreeLM is running; they do not wake a sleeping/closed computer.

## Group participation and mentions

Type `@` in the group composer to choose a participant. Successfully resolved mentions display in bold after sending and carry the participant's stable host ID and bot ID separately from the text. Typed names and addresses also resolve when exactly one participant matches; ambiguous names must be selected explicitly. References inside code, links, and URLs are not mentions. All group participants still receive the human message: a mention tells them who is addressed rather than hiding the conversation from everyone else.

Bots can answer, react, or call `bot_silence` without adding an empty message. They are instructed to contribute when relevant, let other participants handle messages addressed to them, and avoid repetitive agreement or greeting loops. A completed bot message offers peers another turn, including text posted in response to a reaction and replies in groups created before this feature. A peer already waiting to see that message does not receive a duplicate turn; queued peer updates are coalesced around the latest context. Silence and reactions alone do not start new bot-to-bot exchanges. Reaction-derived peer turns retain the reaction's tool restrictions throughout the exchange; a text acknowledgment cannot escalate an emoji into new task authorization.

Group details allow a limit of 1–100 automatic peer-triggered turns per human message, with a default of 12. This counts evaluations, including silent ones; every participant's initial opportunity to consider the human message is outside that limit. At the limit, the group pauses automatic follow-ups and shows that state. **Stop** cancels the group's pending work. A new human message starts a fresh round; sending, editing, or unsending a triggering message cancels its superseded group replies. The original human request remains the scope of tool authorization: a bot's text or mention does not grant new permission to run tasks, create schedules, or take external actions.

## Asking a bot to message a group

In a private conversation, you can ask a bot to initiate a message in a group it belongs to, for example, “Ask the group in #general if they need anything.” `bot_groups_list` discovers current member groups on the bot's home host and connected hosts. It accepts a title query with an optional leading `#`; case does not matter. An empty group can be discovered before it has any history. The result includes the coordinator's host ID and conversation ID, so groups with the same name remain distinct. Historical cached groups are not treated as live destinations.

`bot_groups_send` takes `host_id`, `conversation_id`, and `text`. The coordinator rechecks membership and whether the sending bot is enabled, writes the message under that bot's own identity, and returns a delivery receipt. It never creates a pretend human message or copies the private conversation into the group. The bot should share only the requested message, resolve an ambiguous group before sending, and distinguish “sent” from a reply received. These tools are offered on direct human-message turns, not group turns or notification wake-ups.

Other group members receive an opportunity to answer, react, or stay silent, including when this is the group's first message. Their replies may wake peers within the existing automatic-reply limit. All evaluations in a bot-initiated exchange count toward that limit. The outreach message does not transfer private-chat authorization into the group: peer turns retain restricted, read-only tools and cannot initiate another group send. **Stop** cancels the exchange and discards late replies. A send is rejected while the destination already has pending group work, so it cannot silently replace an active discussion.

Local delivery is a quick synchronous mailbox action; delivery to another connected host runs as a durable background job. A host-generated operation ID makes retransmission idempotent across restarts. Reusing that ID with different content is rejected. An unreachable or outdated coordinator reports an error instead of falling back to a human-authored send. Successful admission means the group message is stored; it does not guarantee that every member is online or will choose to respond.

## Recalling group conversations privately

When you message a bot privately, it receives bounded, relevant excerpts from groups it belongs to. This uses existing saved group conversations immediately; it does not depend on the bot having called `bot_remember`. `bot_groups_search` searches that bot's group history (an empty query lists groups), and `bot_groups_read` pages through complete messages to recover details outside the automatic excerpts. These tools are independent of Chat/Code history access and personality learning, which govern separate data sources.

Membership is checked by both host ID and bot ID. Other bots' private conversations and groups the bot does not belong to are excluded. Recollection is available in direct conversations only: private messages and other groups' histories are not automatically shared into a group reply. Retrieved discussion is historical context, not new authorization or proof that a proposed task was completed.

Local history is read from the current mailbox, so edits, unsends, and deleted groups affect subsequent recollection. Connected hosts are queried for current group histories, including groups created before this feature. Only verified snapshots replace a remote host's cached observations; an unavailable host does not look like an empty history. Remote histories also carry coordinator provenance on group turns between updated hosts. Older peers receive the compatible original request shape.

For disconnected coordinators, the bot retains bounded, timestamped last-observed excerpts across restarts (up to 80 messages / 60,000 content characters per observed group, and 2 MiB / 256 observations overall). These may be incomplete or stale: remote edits/deletions cannot be reflected until the coordinator is reachable or sends fresh context. Full older remote history requires a live connection from the bot's home host to the coordinator; observations cannot recover unreceived history. Deleting a bot removes its cached observations. Transcript recollection itself requires no model-generated summaries; durable learning below is a separate model-assisted operation.

## Persistent memory and experience

Each bot also has its own durable memory records, separate from transcript excerpts and learned personality. **Persistent memory** is on by default for existing and new bots, independently of **Personality learning** and **Chat/Code history access**. Records retain facts, decisions, preferences, relationships, tasks, and lessons with their source host, conversation, and supporting message IDs. They live on the bot’s home computer in its profile and survive restarts, transcript cache eviction, and conversation deletion. Deleting a conversation removes its transcript, not knowledge already saved from it; use **Saved memories** or an explicit forget request to remove that knowledge. Deleting the bot removes its records.

Eligible activity queues background consolidation of newly observed messages through the bot’s configured model and thinking mode. The durable queue stores source identifiers, resolves the current source and configuration at execution, and resumes after restart. Foreground replies preempt extraction and use memories already saved; learning resumes after the reply. Silent group participants learn too. A private conversation can also backfill up to two relevant or recent group sources per turn, allowing existing groups to produce saved knowledge. This is incremental learning as the bot participates or is contacted, not an always-running background training process. Per-source revision cursors avoid repeatedly processing unchanged messages. Source edits and unsends invalidate records tied to the changed evidence; reactions and read receipts do not. A saved memory remains a textual record, not a model-weight update.

Each extraction request uses the endpoint’s strict JSON-schema format and separately validates the result before saving. It is bounded to at most 24 completed source messages, 48,000 input characters, 12 extracted notes, and the configured model context budget. Notes are at most 2,000 characters and each bot can retain 500; reaching capacity reports an error instead of silently evicting older knowledge. The extractor receives that source’s existing notes and the bot’s identity/participant roster so it can attribute experiences correctly. Instructions preserve hypotheses versus verified results and open versus completed tasks, and prohibit credential storage or treating historical discussion as new action authority. Extraction adds background model calls but does not delay the normal reply’s **Thinking** phase. Provider, schema, timeout, and capacity errors are nonfatal to the normal reply and appear under **Saved memories**; they do not falsely mark failed learning as complete.

Relevant saved records are included in later replies. In a private conversation, a bot can recall its own records from both direct messages and groups. Inside a group, only that group’s records are exposed; private conversations and other groups are not shared. `bot_memory_search` reads durable records, `bot_memory_save` creates or updates a stable key with visible source citations, and `bot_memory_delete` forgets a record. Keys are scoped to the source host and conversation, so matching keys in different groups cannot overwrite each other. Reaction-derived turns expose search only, not memory mutations.

Open a bot’s details and **Customize** to toggle **Persistent memory** or review **Saved memories**. Saved records show their kind and source, support search, and can be edited or deleted; those edits save immediately. Disabling memory stops automatic learning, memory context, and memory tools while preserving records for later re-enabling. Explicitly removed records are not recreated merely by re-reading unchanged messages already processed. Updated connected hosts expose these controls through the existing authenticated bot connection; older hosts must update first.

## Persistence and execution

`electron/bot-host.ts` owns `~/.freelm/bots/workspace.json` (under `FREELM_HOME` when configured). The file uses atomic writes and a serialized mutation queue. It contains profiles, durable memories, learning cursors, conversations, drafts, reactions, and reply states; API credentials remain in existing connection storage. Model work runs outside the writer so separate conversations can progress independently. A durable message ID makes retries idempotent. Pending replies become retryable failures after a process restart.

The renderer uses the existing chunked workspace transfer to avoid Electron bridge truncation for large histories. Snapshot revisions prevent older polls from replacing newer accepted mutations. The host mailbox is bounded at 64 MiB with per-field/conversation limits; this foundation does not yet page old message history.

Native requests support `/responses`, `/chat/completions`, and the configured `/chat` alias with the selected explicit thinking mode. Reply requests inherit the app's cold-load deadline. The bot's optional function tools include `bot_react`, `bot_remember`, and the thread tools below; learned notes are visible and editable. Providers that explicitly reject tool definitions can still return text. Provider failures are shown on a retryable message instead of silently dropping the reply.

Conversation text is sent without transport headers. Message IDs, reply targets, and host-qualified group authors are provided separately as internal context for tools such as reactions. Bots are instructed to return conversational text. A narrow cleanup removes standalone leading UUID-based `[message_id: …]` headers echoed by older prompts, including from displayed history, without rewriting saved historical messages. User text, code blocks, inline mentions, and intentional `message_id` examples requested by the user are preserved.

History access supplies bounded summaries/excerpts from up to 30 recent non-temporary Chat/Code threads on the bot's home host. It excludes attachments, tool payloads, API credentials, and project filesystem access. This automatic context is supplemented by explicit, paginated thread search/read tools over the complete active Chat/Code transcripts (including older threads). Temporary chats remain excluded. Users can disable thread context and tools per bot. Thread excerpts and other participants' messages are identified as untrusted conversation data in the prompt.

## Remotes

Bots extend the existing authenticated FreeLM remote protocol; they do not expose a separate unauthenticated service. `/info` advertises `bots: 1`, `botNotifications: 1`, and `botGroups: 1` for group rosters, resolved mentions, optional participation, and peer-message notifications. `GET /bots` provides a validated credential-redacted snapshot; `POST /bots/command` performs durable mutations; `POST /bots/respond` runs one host-owned bot for a group. `POST /bots/watch` observes a subscription through the bot's home host and rechecks its thread-access permission. Remote group requests require valid bounded transcripts and results, including roster membership for message authors and mentions. Cancellation propagates over the HTTP connection to the evaluator. Older hosts report that an update is needed for the new group capabilities; ordinary direct replies retain their existing compatibility.

Groups should normally live on the local coordinating host, which already has connections to the participant hosts. If a group is created on a remote coordinator, that computer must itself have connections to every other participating host.

`botGroupReadOnly: 1` additionally advertises support for reaction-derived `group_message` notifications marked `readOnly: true`. The client requires this capability before sending those restricted follow-ups, so an older peer cannot lose the reaction's permission boundary. Ordinary peer-message turns still need only `botGroups: 1` and `botNotifications: 1`.

`botGroupOutreach: 1` advertises bot-authored group roots and authenticated `POST /bots/group-send` delivery. The sender's home host supplies its identity and stable operation ID; the coordinator rejects attempts to impersonate one of its own local bots and verifies the remote author's enabled profile. Peers must support outreach roots before receiving one, so an older client cannot reinterpret the bot message as a human request. The delivery receipt contains only destination IDs, message ID, creation time, and deduplication status.

## Thread coordination tools

- `hosts_list`, `projects_list`, `models_list` discover valid targets without returning API credentials.
- `threads_list`, `threads_search`, `threads_read` provide paginated, bounded history and live task status. Search is literal and case insensitive; temporary chats, media payloads, and provider replay are excluded.
- `threads_create` creates and starts Chat or Code, optionally in an existing project with a chosen configured model. `threads_send` durably queues a follow-up. Code consumes queued input at a safe tool boundary; Chat waits for the current answer.
- `threads_read` also returns bounded attachment metadata from user attachments and completed tool outputs. Bots can pass the returned `attachmentRefs` to `threads_create` or `threads_send` to reattach existing images or text documents, including older reference images. The actual contents resolve on the destination computer and never enter the bot's text tool result. Up to six references and 64 MiB total are accepted; each asset must be at most 32 MiB, and image input requires an image-capable destination model. References are host-specific: forwarding between threads on the same computer is supported, while cross-host refs, arbitrary URLs/paths, temporary-thread assets, and deleted assets are rejected. Computer-use screenshots are excluded.
- `threads_wait` waits for completion, error, or a human question/approval, with cursors and cancellation. `threads_rename`, `threads_archive` (including restore), and `threads_stop` manage existing work. No permanent deletion or approval-answering tool is offered.

Each tool accepts an optional stable `hostId`; omitted means the bot's home computer. IDs from one host must not be used on another. Authenticated `/bots/task` executes only on its addressed host and advertises `botTasks: 1`; it cannot proxy onward. A remote bot can reach only the instances connected on its own computer.

Delegated thread execution runs in the host process through `HostTaskService`, using the shared agent loop, system prompt, tool host, compaction, model settings, and permissions. It continues when the workspace window is closed or displaying another computer, as long as FreeLM itself is running. Renderer-owned and host-owned runs use explicit ownership to prevent competing execution; workspace updates merge independent changes and surface conflicts rather than overwriting drafts or results. Human questions and tool approvals pause for the user and reappear when the window is opened. The bot cannot answer them on the user’s behalf.

New Code tasks use **Ask for approval**. Existing tasks retain their own permissions and model. Remote bot requests also respect the target host’s “Allow connected FreeLM clients to use these tools” switch before starting Code work. Bots cannot change permission modes, approve requests, or answer questions directed at the human. Instructions distinguish user requests from untrusted retrieved content and prohibit using delegation to evade a denial. Work already accepted into a thread remains there if the bot is cancelled; use `threads_stop` to stop that task explicitly.

Bot replies now run an abortable tool loop without the previous four-round cap. Tool outputs are bounded, API reasoning/call-result pairs are retained, and reaching the configured model context budget stops with an explicit continuation error. Thread create/send operations use stable host-generated operation IDs from the bot action journal, independent of provider call IDs. Waits are bounded to 60 seconds per background job; model requests retain the transport cold-load deadline. A provider failure does not discard completed action results.

## Responsive execution and recovery

`bot_send_message` sends an ordinary text bubble immediately and lets the same turn continue working. For fresh human requests that need investigation, tools, or delegation, the prompt directs the bot to send a brief acknowledgment of its intended next step before extended planning or work tools, then continue working. Useful progress and blockers can be sent during the work, with a concise verified result afterward. Acknowledgment is not completion: the bot must not stop merely because it has said it will act, claim a task started before admission, or invent an ETA. Simple answers, peer chatter, reactions, and quiet notification checks do not need extra acknowledgments. This is model guidance, not a canned host-generated reply; initial model latency still applies.

Messages do not expose private reasoning. `bot_silence` can finish without another bubble once the exchange is complete or background/delegated work has been accepted and its completion is tracked. New private messages steer the active reply at safe boundaries: inference can be interrupted, and unstarted calls in an obsolete batch are cancelled before the correction is admitted. A running synchronous action reaches its boundary first. Group turns retain their existing superseding-round rules.

Quick operations return results directly: memory/history lookups and changes, reactions, messages, scheduling admission, thread creation/message admission, and zero-timeout thread polling. Long waits and external plugin operations return a durable job ID immediately. Plugins default to asynchronous execution; authors can declare a genuinely quick operation `execution: 'sync'`. `threads_wait` is async unless `timeoutMs` is zero. Background completion wakes the bot, which can read the saved result with `bot_jobs_get` and send a concise update. `bot_jobs_list` and `bot_jobs_cancel` manage work in the current conversation.

The conversation drawer shows active jobs and exact tool arguments, approval controls, errors, and Stop job. Completed work is available in conversation details. **Stop reply** stops that response; it leaves already-admitted jobs and delegated threads running. Use **Stop job** for a background operation and `threads_stop` for a delegated Chat/Code task. Disabling a bot or withdrawing its triggering message also cancels its outstanding background operations.

Plugin grants control which tools are available. They do not approve each consequential action: mutating, unknown-effect, or explicitly approval-required plugin calls wait for direct human approval of the exact saved action. Approval cannot come from model arguments. Grants and bot availability are checked again before execution. The stable `operationId` is available to local plugin code and forwarded to MCP for integrations that support idempotency.

`workspace.json.execution.json` stores run checkpoints, original pending tool calls, action identities, results, approvals, jobs, and notification receipts independently of reply bubbles. Retry resumes the saved provider context and reuses completed results. After interruption, unfinished read-only operations can resume; a potentially completed mutation becomes **outcome unknown** and is not automatically repeated. Cancellation is not proof of rollback. This is conservative recovery, not a claim of exactly-once execution against arbitrary external services. The journal is bounded and fails explicitly at capacity without evicting recovery records.

`bot_history_search` and `bot_history_read` retrieve older private conversations with the same bot on its home host. They are independent of the Chat/Code history toggle, exclude other bots’ DMs and unsent content, and are unavailable in group turns. Retrieved messages, peer bot text, and learned personality are marked as data; the system prompt describes only capabilities actually offered in that provider iteration, including after tool fallback.

Updated peers advertise `botRuntime: 1`. Immediate text messages stream as separate events, with ID-based replay deduplication. Source-qualified jobs appear on the conversation coordinator and terminal job notifications are persisted once. Older peers retain ordinary replies, but must update before asynchronous remote jobs or job approvals can run. Remote messaging still uses the existing authenticated host connection; source IDs identify scope and are not a substitute for transport authentication.

The native smoke launches an isolated Electron profile against a loopback fixture provider, verifies both provider formats, background replies, reaction notifications/edits, read receipts, redaction, and durable storage. The task smoke also checks attachment forwarding into real provider request bodies and an asynchronous task-completion reply. Neither calls the user's models or modifies their profile. Set `FREELM_SMOKE_EXECUTABLE` to a packaged FreeLM executable to run either smoke against the signed app. The persistent-memory smoke additionally extracts records for both provider APIs, verifies on-disk source attribution, deletes only its fixture source group, restarts, and checks fresh direct-message recall from saved records without transcript excerpts. Browser fixtures prove rendered interaction flows; they are distinct from real provider and remote deployment checks.

The large-workspace smoke uses synthetic history and repeated media references totaling over 3 GB when serialized, without real providers or user data. It checks startup, initial synchronization, autosave, and continued renderer responsiveness. Host notifications carry a workspace revision so unchanged workspaces do not require another full transfer; merging compares structure without serializing the whole media-rich workspace into one string.

### Task follow-ups and message receipts

Bot replies default to short, conversational text messages, including technical answers and task follow-ups. The shared system prompt discourages report sections, headings, tables, and bullet lists unless the user explicitly requests a structured format or deliverable. Sparse inline emphasis, code, and links remain available. The bot paraphrases verified task results in its own voice and treats verbose history, tool reports, and notification summaries as facts rather than a style to imitate. These are model instructions, not a Markdown filter: requested formatting and existing messages remain intact, and important blockers or uncertainty must still be communicated.

Explicit `bot_send_message` calls become immediate bubbles; the final assistant response becomes the concluding reply. Ordinary intermediate tool-round text stays in the model's working context and is not a substitute for the immediate-message tool. Message IDs, targeting, and reactions remain separate metadata.

Sending or creating a Chat/Code thread automatically subscribes the bot to its completion or attention state. `threads_wait` retains subscriptions for active work, and `threads_watch` can subscribe to an existing thread. The host saves subscriptions in the bot mailbox, checks statuses without model calls, and wakes the bot only for a changed completion, failure, or human-attention state. Notifications reference the original human request; task output is untrusted data, not new authorization. Completed subscriptions are removed; human-attention states remain watched until the task later completes. Connection failures are reported once per distinct failure and retried after reconnection. Watches start even if FreeLM opens in Home or Code. They require FreeLM's local workspace/runtime to be available; subscriptions resume after restart, but do not run while the app is closed. Remote subscriptions are observed through the bot's home host and its existing authenticated connections.

Human reaction additions, changes, and removals notify the author of a bot reply (or all participants for a human message). Pending changes to the same reaction are coalesced. The bot may acknowledge silently with `bot_silence`; reaction events expose no mutating thread tools, and an emoji does not authorize work. Turning off thread access retires subscriptions and pending thread notifications. Older remote hosts require an update for notifications.

Outgoing messages show **Delivered** with no timestamp until the addressed bots have consumed that message revision. Then they show **Read** with the latest participant's read time. For remote bots the receipt arrives with the completed response, so delivery remains visible while waiting. Editing a message clears its prior receipts. Incoming message timestamps remain unchanged. Historical receipts are not fabricated.

### Thinking and writing

Pending bot replies track queued, thinking, and writing separately. Reasoning, waiting for the provider, and tool execution show an animated lightbulb and **Thinking** beside the conversation name. Queued participants do not appear to be thinking yet. The three-dot message bubble appears only when the provider streams reply text; it returns to Thinking if the model resumes reasoning or calls a tool. The final text arrives as one message, and both indicators clear on completion, failure, or cancellation.

Bots request streaming from Responses and Chat Completions providers. JSON-only providers remain in Thinking until their complete reply arrives; there is no simulated typing delay. Updated remote hosts relay bounded activity events using the authenticated bot response stream, advertised as `botActivity: 1`; older hosts keep their JSON compatibility. Local mailbox changes notify the renderer immediately rather than waiting for the periodic refresh. Storybook includes interactive phase previews, and `test:bot-activity` checks the native transport and UI against controlled streams for both provider protocols.

### Conversation presentation

The conversation header stays over the scrolling history with a translucent, blurred background. New message bubbles enter with a short animation; opening existing history, refreshing the mailbox, and reacting to a message do not replay it. Reduced-motion preferences disable the entrance animation.

Long bot replies start with a preview about ten body-text lines tall. **See more** expands the original Markdown, and **See less** collapses it again. This only changes presentation: copy, reply targeting, stored history, and provider context retain the complete message. User messages remain uncollapsed. Storybook's **Long Reply** and **Narrow Long Reply** states include a **Receive a reply** control for checking the collapsed layout, scrolling header, and arrival animation.
