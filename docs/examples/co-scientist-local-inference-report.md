# Research proposal

Two hypotheses address whether a local multi-agent system on a single RTX 4090 can cut inference latency without sacrificing answer quality. H1 asks whether CUDA-stream concurrency enables true decode-kernel overlap across separate 7B Q4_K_M instances (a systems question with no published answer). H2 asks whether a two-agent 2K-context architecture with a 1B span router preserves ≥90% hop-coverage on HotpotQA (distractor) while exploiting the linear bandwidth saving from context reduction. Neither hypothesis has been empirically tested; all latency figures are component-level calculations, not measurements.

## 1. CUDA-stream concurrency on a single 4090 produces true kernel-level overlap between separate 7B decode processes, reducing P50 wall-clock by >100 ms over a sequential-execution baseline.

Plausible but unverified. GPU kernel serialisation on a single SM array predicts no overlap absent explicit stream concurrency; vLLM's multi-instance feature targets throughput under concurrent user load, not single-query multi-model latency. The question is genuinely open for consumer GPUs with 128 SMs.

**Next experiment:** On one RTX 4090, run Llama-3-8B Q4_K_M in three configurations on 500 GSM8K + 500 MultiArith (regex decomposition, 128-token cap): (B) single 7B, 150-token CoT; (C-serial) three 7B instances, 50-token subtasks, sequential processes; (C-parallel) same three instances via CUDA streams or MPS. Measure P50/P95 wall-clock, per-task EM, peak VRAM, and nsys kernel-trace to confirm whether decode kernels from different instances overlap in time. Reject H1 if (C-parallel) P50 ≥ (C-serial) P50 − 100 ms or per-task accuracy drops >5%.

## 2. A two-agent ≤2K-context architecture with a 1B span router preserves ≥90% hop-coverage on HotpotQA (distractor) despite a ~1.5–2 s router overhead, justifying the latency penalty over simple truncation.

Mechanistically well-supported (bandwidth-bound prefill makes 8K→2K a real linear saving), but the router's span-selection accuracy is untested. The hypothesis honestly predicts (C) is slower than (B); the question is whether hop-coverage justifies the penalty.

**Next experiment:** On one RTX 4090 with Llama-3-8B Q4_K_M + 1B Q4_K_M router, run 500 HotpotQA distractor questions (2 gold passages, no retrieval step) in three configurations: (A) single agent, 8K, both passages; (B) single agent, 2K, truncated; (C) two 8B agents (2K each, one passage per agent) + 1B router. Max 512 generation tokens per agent. Measure P50/P95 wall-clock (including router + inter-agent memory-copy), EM/F1, hop-coverage, peak VRAM. Reject H2 if (C) hop-coverage <90% or EM/F1 drops >5% vs (A). Secondary: if (C) P50 > (B) P50 + 1 s AND hop-coverage <90%, the wrapper is strictly worse than truncation.

## Limitations

- Neither hypothesis has been empirically tested. All latency figures (1.6 s prefill at 8K, 0.4 s at 2K, 1.5–2 s router overhead, ~2.85 s total for H2-C) are component-level calculations from published latency models, not measurements on the target hardware.

- No published data exists on true concurrent execution of two or three separate LLM model instances on a single consumer GPU with wall-clock latency or nsys kernel-trace evidence (H1's core mechanism is unverified).

- No baseline exists for 1B-model span-routing accuracy on HotpotQA evidence spans; the ≥90% hop-coverage target is a design assumption, not a measured quantity (H2's critical quality risk).

- H1's VRAM budget (15.3 GB weights + 8.7 GB KV-cache headroom) is tight; preemption-swap under longer-than-expected subtask outputs could invalidate the comparison, though the 128-token cap mitigates this.

- H2 eliminates the retrieval confound by using HotpotQA's distractor setting (gold passages provided), but in deployment the 1B router would also face retrieval-error propagation, which is not measured here.

- The four preserved sources provide mechanistic or feasibility support only; none directly measures the specific multi-model or multi-agent configurations proposed.
